# ORBITAL 项目现状审计与重建规划

更新日期：2026-09-22

## 1. 当前结论

当前工作区已经不是一个完整的 Storefront + Commerce 应用，而是一个可以独立运行的静态参考站点，以及一层保留的服务网关代码。

现阶段不应继续补商品、账户、订单等业务功能。先把视觉基线、入口行为和未来架构边界固定，再决定是恢复应用代码，还是以现有静态站点为基础重建。

## 2. 现存内容

- 根目录：`server.mjs`、根 `package.json`、pnpm 锁文件、开发 compose 文件。
- 静态页面：`references/TraeWEBTEST/pages/` 下的首页、塔罗、星座、易经、设计预览，以及新的 `ghost-fibers.html`。
- 静态资源：品牌 CSS、三张 PNG、塔罗 SVG，以及 `ghost-fibers.js`。
- 网关：公共入口固定为 `http://localhost:3002`，负责静态页面与资源服务。
- `/shop`、`/account`：当前明确返回 404，旧商城和账户页面已退出公共入口。

## 3. 已确认缺失的部分

以下内容不应假设仍然存在：

- `apps/storefront` 的 Next.js 源码与依赖清单。
- `apps/commerce` 的 Medusa 源码、数据库模型和迁移。
- 用户、商品、购物车、结账、订单、支付与后台管理实现。
- 应用层的测试、类型检查和生产构建入口。

根 `package.json` 当前只保留静态站点启动脚本；未来恢复应用服务时，再单独补回对应的构建、数据库和业务命令。

## 4. 当前端口约定

| 用途 | 端口 | 当前状态 |
| --- | ---: | --- |
| 公共访问 / 静态网关 | 3002 | 当前启用 |
| Storefront 内部服务 | 3010 | 仅在恢复应用后启用 |
| Commerce 内部服务 | 9001 | 仅在恢复应用后启用 |

所有浏览器访问统一走 3002。3010 和 9001 只作为内部服务端口，不能再作为用户入口。这解决了此前 `pnpm dev` 与 `server.mjs` 的端口约定分裂问题。

## 5. 分阶段计划

### Phase 0：基线冻结

1. 保留现有静态页面和参考资源，不引入业务功能。
2. 统一公共入口为 3002。
3. 确认 `/shop` 和 `/account` 不再被服务。
4. 记录现存页面、资源和已缺失能力，避免后续把历史代码当作现状。

### Phase 1：产品与信息架构

1. 明确 ORBITAL 的核心产品：手串/随身物与东方命理内容的结合方式。
2. 确定首发范围：内容浏览、商品目录、商品详情、购物车、结账、账户是否同一阶段上线。
3. 重新定义页面层级、导航、SEO 路由和移动端优先布局。
4. 先产出数据模型和接口契约，再选择实现技术。

### Phase 2：应用骨架

1. 新建可验证的 Storefront 应用，而不是依赖当前空的 `apps/storefront` 目录。
2. 新建 Commerce 服务与数据库，再接入真实商品和订单数据。
3. 保持 3002 网关作为统一入口，内部服务分别使用 3010/9001。
4. 先完成健康检查、错误页、日志和最小化部署启动链路。

### Phase 3：业务闭环

按优先级依次实现：商品目录 → 商品详情 → 购物车 → 结账 → 订单 → 账户 → 管理后台。每一步都需要配套接口、权限、异常状态和测试。

### Phase 4：上线准备

补齐支付、邮件、库存、隐私政策、退换货、监控、备份、域名、HTTPS 和生产部署，并进行移动端、可访问性、性能和安全验收。

## 6. 当前暂不做的事项

- 不恢复旧商城或账户页面。
- 不把静态参考页伪装成可购买的商城。
- 不在缺少数据模型和服务源码的情况下继续编写订单、支付或认证功能。
- 不改变已确认的 GhostFibers 背景视觉基线。
